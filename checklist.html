公共物品 grant 申请 · 40 项校验清单

Public Goods Grant Application — 40-Item Pre-Submission Checklist ｜ CC BY 4.0 ｜ v1.0

用途：提交前自查，也是 GCC Cohort 5 可选的初审工具。每一条都写死「怎么判定通过」，不靠感觉。

来源：Conflux Integration Grants 36 份提案逐份核对（论坛 37 个 topic，其中 1 个是官方模板帖；4 批 / 15 拒 / 3 改 / 14 无结论），加上 GCC Cohort 2–4 的表单要求。

用法：任何一条判否，先改再提交；判不出（无法核）按判否处理。

A. 问题与因果链（1–6）

#检查项判定方式（怎么算通过）证据
1一段话讲清要解决的具体问题把项目名换掉后这句话仍然成立 → 判否。必须绑定具体场景、具体人首段
2受损方与损失可量化出现至少一个数字或一个可查事件，并给来源；只有形容词 → 判否首段或问题段
3说明这是本生态的问题问题句与「本生态/华语区」有唯一对应；换成任何开源项目都成立 → 判否问题段
4证明现状未被解决列出 1–2 个已有尝试，并说明为何不适用；没有 → 判否问题段
5不靠形容词支撑「赋能/生态繁荣/影响力/生态位」类词全篇 ≤2 个，且每处旁边有数字；超了 → 判否全文检索
6每个问题句都对应一件交付物每个问题句能画线到某个交付物；画不出的问题句删掉再提交对照 C 段

B. 里程碑（7–13）

#检查项判定方式（怎么算通过）证据
7所有里程碑都从签约之后开始最早里程碑日期晚于签约日；把「原型/设计/调研已完成」计入 → 判否（会被砍成 pre-grant work）里程碑表
8每个里程碑有一个唯一交付物用一句话说出「打开能看到的东西」；说不出的 → 判否里程碑表
9里程碑可独立验收验收方不开会、不看演示也能判通过；需要演示 → 判否里程碑表
10第一个里程碑在 60 天内可达签约日到 M1 日期间隔 ≤60 天；超过 → 需拆日期
11里程碑总数 ≤4数行数；>4 → 合并里程碑表
12每个里程碑写明怎么核至少给出链接/文件/链上记录之一；只写「完成开发」→ 判否里程碑表
13依赖关系写明若 M2 依赖 M1 的产出，正文写明依赖；没写 → 补一句里程碑表

C. 预算（14–21）

#检查项判定方式（怎么算通过）证据
14总额 = 分项之和逐行相加，误差必须为 0；差 1 U 也要改预算表
15每项有人力单价或数量出现「N 小时 × 单价」或「N 份 × 单价」；只有一个总数 → 判否预算表
16「其他/杂项」≤5%杂项金额 ÷ 总额；超 5% → 拆开预算表
17每笔预算能落到某个里程碑反查：某笔钱对应的交付物不在任何里程碑里 → 判否对照 B/C
18手续费/平台费写明跨币种或走中转时显式列出；没有 → 补一行预算表
19不含 pre-grant work预算项对应交付物的日期全部在签约后；有历史工作 → 移出预算对照 B
20立即解锁 + 里程碑 = 100%相加等于 100；不等 → 判否资金段
21单项占比无异常单一人力项 ≤60%，超了需一句解释（研究型项目可例外但要写明）预算表

D. KPI（22–28）

#检查项判定方式（怎么算通过）证据
22指标是生态专属数字指标名含生态专有对象（如本链的交易/地址数、本基金会的华语项目数）；写成「用户增长」→ 判否KPI 段
23每个指标有基线写出当前值，或明写「当前为 0，从 0 起」；没有 → 判否KPI 段
24每个指标有目标值和时间点数字和日期必须同时出现；只有数字 → 判否KPI 段
25指标能从公开数据核给出数据源（浏览器/仓库/表单/公开看板）；给不出 → 判否KPI 段
26指标不能自己单方面刷「发 10 篇推文」「开 2 场会」不算指标；外部可观测才留KPI 段
27指标数量 ≤5数个数；>5 → 删到能记住KPI 段
28失败条件写明出现「若到 X 日未达到 Y，则……」；没有 → 补一句（这条最能提高可信度）KPI 段

E. 可验证交付物（29–34）

#检查项判定方式（怎么算通过）证据
29每件交付物有能打开看的形态链接 / 文件 / 合约地址三者之一；只有描述 → 判否交付物清单
30许可与归属写明出现许可证名（CC BY 4.0 / MIT）或「归生态所有」；没有 → 判否交付物清单
31交付物在验收时可访问现在点一次能打开；打不开则必须写明「签约后 N 日内公开」，且 N ≤7链接
32涉及第三方数据有脱敏说明出现具体脱敏方式（去名/去金额/聚合）；没有 → 补交付物清单
33附件与正文一致正文提到的每个文件名都在附件里存在；缺 → 补或删提法附件
34不把演示/会议当唯一交付物交付物清单里至少一件是持久文件交付物清单

F. 团队与合规（35–40）

#检查项判定方式（怎么算通过）证据
35成员真实可核署名与公开账号/GitHub 一致；不能核的明写「首次公开」团队段
36不冒用他人能力团队段写的每项技能，能在该成员公开作品里找到对应；找不到 → 删团队段
37是否拿过同生态资助写明是/否明确；拿过的写项目名与金额团队段
38与评审方的关系声明出现一句关系声明（无关联/曾参与/合作中）；没有 → 补团队段
39商业化与回馈两栏都填两栏非空；回馈要写机制（比例/周期/凭证），不能只写「愿意」其他段
40推荐人如实有则写姓名+关系+联系方式；没有则明写「无推荐人」并给替代信用机制（如自愿里程碑 60/40）；留空或编造 → 判否其他段

提交前 6 步

  1. 40 条过一遍，判否的先改；判不出的当判否。
  2. 金额、立即解锁比例、里程碑比例、截止日四处对齐（例：5,000 / 60% / 40% / 2026-12-31）。
  3. 附件导出一份 PDF，文件名与正文提法一致。
  4. 所有链接点一次，确认能打开。
  5. 推荐人段原话保留，不要删成空白。
  6. 提交后 24 小时内不要改稿——评审可能已经开始读。
